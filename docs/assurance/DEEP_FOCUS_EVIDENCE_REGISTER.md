## 2. How to Use This Register

### 2.1 Status and verification

Status describes evidence availability. Verification status describes whether the artifact and its context were checked. A captured artifact may document a failure or open risk; Captured does not mean Passed.

Allowed statuses: Pending, Pending Indexing, Pending Future, Captured, Verified, Needs Review, Not Applicable.

### 2.2 Evidence record minimum

For every new record, preserve the exact artifact location, commit/build/device context, date, responsible person, expected result, actual result, and review outcome. Redact secrets and personal user data. Prefer a durable repository artifact or restricted evidence location linked from this register.

## 4. Evidence Capture Record Template

| Field | Required entry |
|---|---|
| Evidence ID / title | Stable identifier and concise name |
| Requirement / test | Linked requirement, risk, control, or test case |
| Build context | Branch, commit SHA, build/version, environment |
| Platform context | OS/version, device model, relevant settings |
| Method | Exact steps, tools and relevant versions |
| Expected / actual | Predefined acceptance condition and observed outcome |
| Result | Pass, fail, blocked, or not run |
| Owner / reviewer | Person who performed and independently reviewed where possible |
| Artifact | Log, screenshot/video, report, test output, issue/PR or store record |
| Data handling | Redaction and classification check |
| Follow-up | Defect ID, retest, risk acceptance, or closure record |

## 5. Review

The owner reviews the register before each release candidate, after security/privacy incidents, and at least quarterly while the product is in active development. Update evidence status only when the linked artifact and its context are available.
