# Deep Focus Agent Instructions

These rules apply repository-wide. Deep Focus protects attention, sustainable
work/recovery, privacy and user control. Keep the experience calm and accessible;
no manipulative engagement, gambling, cash rewards or unnecessary pressure.

## Before editing

1. Read [AI rules](docs/AI_RULES.md) completely, then the execution policy and
   Definition of Done it routes to. Use [the documentation map](docs/DOCUMENTATION_MAP.md)
   to select relevant contracts; read selected instruction files completely.
2. Inspect current source/configuration, package scripts and dirty work. Approved
   documents describe intended behavior, not proof it has been implemented.
3. Confirm authorized scope, approved phase and task-relevant owner subdecisions.
   Follow the V1 implementation plan's dependency order; do not skip foundations.
4. Record one outcome, acceptance criteria, allowed files, risk and actual checks
   using [the task brief](docs/ai/TASK_BRIEF_TEMPLATE.md). State the intended scope.
5. Read [engineering guardrails](docs/ai/ENGINEERING_GUARDRAILS.md) for code,
   configuration, architecture/security design or changes to those rules.

## Authority and safety

- Canonical topic contracts and precisely recorded owner amendments govern the
  product. Revision/research drafts are not blanket approval; follow the map's
  reconciliation rules. Flag conflicts rather than choosing a convenient source.
- Preserve existing behavior and unrelated user work. No unapproved scope,
  architecture/provider/major dependency change, large rewrite or destructive
  action. Git examples do not authorize commit, push, pull/merge or deployment.
- Keep secrets/private credentials out of code, logs and public clients; enforce
  ownership/authorization on trusted infrastructure. Do not guess security or
  production policy. Follow guardrails and the relevant security/data contracts.
- Core focus is independent of AI. Apply only exact user-confirmed AI proposals.
  No ads during active focus/recovery; no client-only trusted reward grants.
- Work alone unless the owner explicitly changes that instruction. No automatic
  model switch, extra agent, paid account or spending is authorized by these docs.

## Execution and completion

Use [execution policy](docs/ai/AI_EXECUTION_POLICY.md) for LOW/MEDIUM/HIGH/CRITICAL
risk, STOP, failure and escalation rules. Stop affected risky writes for material
conflicts, missing authority, potential data loss/exposure or unexplained
regressions; bounded safe diagnosis may continue. HIGH/CRITICAL require independent
review before acceptance/integration; self-review is not independent review.

Implement small coherent slices with relevant tests. Inspect scripts rather than
inventing commands; installation and reset-project are not verification. Review
the full task diff including new files, update affected docs/changelog and report
actual evidence, unverified behavior, assumptions and risks. Use focused
Conventional Commits only when committing is authorized.

[Definition of Done](docs/ai/DEFINITION_OF_DONE.md) owns completion and handoff.
Implemented, verified, reviewed and production-ready are distinct. Never claim
tests/security/release readiness that were not established. Keep the user-facing
summary concise, include unresolved gates and the next dependency-safe step.
